# Решение

## Что сделано

- Сохранён существующий публичный API роутера, store, event и sender.
- Добавлена поддержка события `billing-refund`.
- Добавлен маппинг имени события для MMP:
  - `billing-payment` -> `purchase`;
  - `billing-refund` -> `refund`.
- Для refund входная сумма остаётся положительной, как присылает платёжка,
  а в payload для MMP передаётся с отрицательным знаком.
- Добавлен статус `GDPR_NOT_APPROVED`.
- Добавлена GDPR-проверка до поиска MMP mapping.
- Явный отказ в согласии даёт финальный `GDPR_NOT_APPROVED`, а отсутствие
  записи о согласии даёт `RETRY`: согласие ещё может прийти позже.
- При `consent_check_enabled: null` проверка включена по умолчанию.
- При `DryRun=1` в payload устанавливается `Sandbox: true`.
- Сохранена валидация положительной суммы для payment и refund.
- Добавлены table-driven тесты для refund:
  - успешная отправка;
  - нулевая и отрицательная сумма;
  - отсутствие mapping;
  - выключенный проект;
  - временная и постоянная ошибки sender;
  - проверка имени события в payload.
- Добавлены table-driven тесты для GDPR:
  - consent отсутствует и событие возвращается на повторную обработку;
  - consent отклонён;
  - проверка отключена явно;
  - `nil` обрабатывается как включённая проверка;
  - GDPR имеет приоритет над отсутствием mapping.

## Как запустить

Нужен Go 1.22 или новее.

```bash
go test ./...
go run ./cmd/router
```

Для другого каталога с JSON-файлами:

```bash
go run ./cmd/router -data ./testdata
```

## Вопросы PM и решения

1. **Что делать, если партнёр не настроил `consent_check_enabled`?**
   PM подтвердил, что согласие нужно проверять по умолчанию. Поэтому `nil`
   обрабатывается как включённая GDPR-проверка: безопаснее не передать данные
   без явно подтверждённого согласия.
2. **Куда отправлять тестовые события с `DryRun=1`?**
   PM подтвердил, что такие события должны попадать только в sandbox MMP.
   Поэтому при `DryRun=1` устанавливается `Payload.Sandbox=true`, чтобы
   тестовое событие не ушло в production.
3. **Что проверять раньше: GDPR-согласие или MMP mapping?**
   PM подтвердил, что GDPR-проверка должна выполняться первой. При отсутствии
   записи или явном отказе mapping не ищется и данные пользователя дальше не
   обрабатываются; отсутствие записи возвращает `RETRY`, отказ —
   `GDPR_NOT_APPROVED`.
4. **Какой знак должна иметь сумма refund?**
   PM подтвердил, что платёжка присылает refund с положительной суммой, как
   у платежа, а в MMP refund нужно отправлять с отрицательной суммой. Поэтому
   валидация принимает только положительную входную сумму, а роутер меняет знак
   только при формировании payload для `billing-refund`.
5. **Что делать, если записи о согласии ещё нет?**
   После созвона PM уточнил, что отсутствие записи не означает отказ: согласие
   ещё не пришло. Поэтому событие не отправляется в MMP и получает `RETRY`, а
   только явный `Approved: false` получает финальный `GDPR_NOT_APPROVED`.

Отдельные refund-сценарии добавлены в unit-тесты. `testdata/events.json` уже содержит
примеры refund и dry-run, поэтому его расширение для выполнения задания не требуется.
